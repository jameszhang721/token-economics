# 从向量化到 RAG、Agent：进阶任务与阶段指标

> 这是 [token 编码八周研究](../README.md#第-0-周先造尺子照这个顺序跑) **之后的独立进阶路线**，不替代 BPB、fertility、overhead gap 的研究任务。先读[文本进入 Transformer 的过程](text_to_transformer.md)，再跑[离线向量检索示例](vector_database.md)。以下大部分是**待做任务**，不是仓库已实现的功能；当前只有字符二元组精确检索及其教学测试，尚无语义 embedding、完整 RAG 或 Agent。

## 一张图看依赖关系

```text
阶段 1：固定资料与带标注问题，建立词面检索基线
    ↓
阶段 2：TF-IDF / BM25 / 稠密 embedding / 混合检索做同场对照
    ↓
阶段 3：文档分块、向量存储、精确检索与可选 ANN
    ↓
阶段 4：取回原文 + 引用来源 + LLM 生成，完成最小 RAG
    ↓
阶段 5：将检索包装成工具，完成可控的单 Agent 循环
    ↓
阶段 6：权限、状态、测试、观测与框架选型
```

**边界先记住：**BM25 是关键词匹配的排序算法，不是语义 embedding；Word2Vec / FastText 学习词向量，但不能直接替代整段文本的检索表示；句子／文档 embedding 可用于语义检索，多向量检索保留更细粒度的信息，代价是存储和计算。RAG 是检索原文后把原文放进提示词，让 LLM **重新 tokenize** 并生成答案；检索向量不直接进入 LLM 的 token embedding 层。Agent 则是在此基础上决定**是否、何时、用什么参数**调用检索等工具；固定检索流程不一定是 Agent。

## 所有阶段共用的实验规则

1. 固定一份可公开使用的本地资料：至少 **3 篇文档、20 个可追溯的片段**；每片段保留 `source`、文档 ID、片段 ID 和正文。至少写 **40 个问题**：30 个资料内可回答（含术语精确匹配和同义改写），10 个资料外不可回答。为可回答问题标注至少一个相关片段 ID 和可核对的答案依据；不可回答问题标记 `answerable=false`。先冻结原始资料版本；阶段 1 对照固定片段，阶段 3 比较分块方案时要将标注映射到新片段或重新标注，不能拿旧片段 ID 直接计分。
2. 将问题固定分为开发集和保留测试集（各 **15 个可回答 + 5 个不可回答**），保存划分及 seed。用开发集确定 `k`、阈值、分块大小、提示词等；不要看测试集结果再反向调参数。保留原问题、标注与每轮预测，才能复查漏召回和误召回。
3. 对可回答问题统一报告 **Hit@k**（top-k 中至少包含一个已标注相关片段的问题占比）和 **MRR@k**（第一个相关片段排名倒数的平均值；未命中记 0），固定 `k=1,3`。如同一问题标有多个相关片段，另报 **Recall@k**（所有问题召回的相关片段总数 / 所有已标注相关片段总数），不与按问题计的 Hit@k 混用。对不可回答问题另报**错误作答率**（本应拒答却给出事实结论的比例），不要把它们混入检索质量指标的分母。
4. 质量和成本同时记录：同一测试集的召回、误召回实例，单次查询延迟 `p50/p95`，索引文件大小，RAG/Agent 阶段的输入／输出 token 数与调用次数。标明运行机器、模型／编码器版本、是否联网、CPU/GPU；比较延迟时必须使用相同设备与资料规模。
5. 下表“验收”是**功能与实验记录的通过条件**，不是声称已经取得的模型效果。质量目标可在开发集上另行设定并提前记录，再用保留测试集验证；达不到预设目标要保留失败案例，而不是改测试集。需要联网下载或 CUDA 的阶段，在当前离线机器上只可标为未验证，不以语法检查代替 GPU 实测。

## 阶段 1：词面向量基线与评测集（离线／CPU）

**任务：**运行现有 `python scripts/vector_search_demo.py`，解释字符二元组词频向量、固定词表、余弦相似度和逐条精确排序；先学习 `VectorStore.from_documents` 等接口，再扩展示例以导入自己的资料（当前 CLI 只支持四条内置文档），建立上述问题与片段标注。构造至少 5 个“字面不同、意思接近”和 5 个“字面相似、意思不同”的误检例子。

**交付：**资料及来源清单、问题／相关片段标注与固定划分、基线检索结果表、两类失败案例分析；记录当前示例 JSON 只作教学存储、没有语义理解或生产数据库能力。

**验收指标：**40 个问题均有可回答性标注，30 个可回答问题均有可核对的相关片段；基线在同一资料和问题集上运行两次，top-3 ID 顺序一致；输出开发集与测试集的 Hit@1、Hit@3、MRR@3，以及 10 个不可回答问题的未命中情况。没有词面重叠时输出空结果，不把零分结果说成“相关”。

## 阶段 2：比较向量化与检索方法（词法 CPU；稠密模型视环境而定）

**任务：**在同一份片段和问题上先比较字符 n-gram、TF-IDF 与 BM25（BM25 不生成语义向量）。再选一个明确支持目标环境的**句子／段落检索编码器**，让文档和问题按照它要求的输入格式分别编码，使用与模型说明匹配的归一化和相似度。阅读 Word2Vec / FastText 的词级表示与聚合限制；试验稠密向量 + BM25 的混合召回（例如 RRF，固定融合参数）。多向量检索列为选做，并记录索引体积和耗时增加。

**交付：**同一问题在词面、TF-IDF、BM25、稠密及混合检索下的 top-3 对照表；模型名称、精确版本、向量维度、预处理、归一化、设备和下载来源；至少 5 条逐例误差分析。不应因工具名称含 “embedding” 就假定实际语义检索已成功。

**验收指标：**每种已运行方法都在冻结的测试集上报告 Hit@1、Hit@3、MRR@3 与 `p50/p95`；明确指出哪个方法擅长术语、哪个擅长改写、混合检索有无改进。重新编码同一文本结果在所选模型的确定性条件下保持一致，查询和文档使用同版本编码器、维度一致；若模型无法取得，稠密／混合项标“阻塞”，**不能**以字符计数向量冒充完成。Python 3.9 / CUDA 11.8 的 GPU 推理要在对应 NVIDIA 机器上单独验证，先核对选定依赖与环境兼容性。

## 阶段 3：分块、向量存储与检索（先精确，后考虑 ANN）

**任务：**设定并记录分块边界、大小和重叠，处理标题及来源定位；保存 `{chunk_id, text, source, metadata, vector, encoder_version}`。对同一编码器分别构建索引和编码查询，做精确 top-k；提供保存、重载、更新和删除后的检查。若规模与查询延迟有必要，再用 FAISS 索引或 pgvector、Chroma、Qdrant、Milvus 等选一种实践 ANN／过滤；它们分别是索引库或数据库／服务，不要求全装。

**交付：**建库与查询命令、索引结构说明、重载前后对照、一次更新／删除记录，以及切换编码器或维度时如何重建索引的操作说明。

**验收指标：**100% 片段都有唯一 ID、原文和来源；维度、版本不匹配时拒绝查询或显式重建，不能静默混用；重载前后固定测试问题的 top-3 ID 一致（同分按固定规则排序）；更新／删除后不会召回已删片段。若引入 ANN，在同一设备上报告对**精确检索**的 Recall@10（对每个问题，ANN top-10 与精确 top-10 的交集比例，再对问题取平均；资料不足 10 条时以实际可返回数为分母）及 `p95` 延迟、索引大小；先记录与精确扫描的对照，不强行要求小资料集必须更快。区分 ANN 的索引召回与对人工标注的检索 Hit@k。

## 阶段 4：最小可核查的 RAG（生成阶段依赖可用 LLM）

**任务：**固定 `问题 → 检索 → 取回原文和来源 → 按 token 预算组装提示词 → LLM 回答`。要求输出答案引用 `source/chunk_id`；资料不足时明确说“不知道／资料不足”。设置 top-k、总上下文预算和片段截断规则；将检索到的文本视为**不可信资料**，不执行其中要求改变系统规则的指令。先用固定／模拟生成器测试拼接、未命中与引用，再在可用模型上验证真实回答。

**交付：**可复现的问答脚本、含引用的答案、不可回答案例、提示词与检索日志（注意不记录密钥或敏感原文），以及词法／语义检索对答案的影响分析。

**验收指标：**测试集每个回答都留有检索片段 ID、最终引用和输入／输出 token 用量；逐条核对 15 个保留集可回答问题的**答案正确性**、**引用是否真实支持该结论**，及 5 个不可回答问题的**拒答比例**，按各自分母报告，不把有引用等同于引用正确。做至少 3 个“检索失败、资料含误导指令、超过 token 预算”的回归测试；任何未获支持的结论都应可定位到失败样例。没有真实 LLM 时只能验收数据流与模拟器测试，不能宣布真实 RAG 回答质量达标。

## 阶段 5：可控单 Agent（不先上多 Agent）

**任务：**把检索包装成 `search_docs(query, top_k)`，定义参数和返回数据格式；实现 `目标 → 判断是否用工具 → 调用 → 校验结果 → 继续或停止` 的有上限循环。保存必要的对话状态，设置最大步数、超时、错误返回与重试边界；有副作用工具必须检查权限并在执行前取得明确审批。检索结果和网页是数据，不是上级指令。

**交付：**一张状态转换图、工具 schema、成功／失败轨迹、审批与拒绝分支测试；如需要才选 LangGraph 等状态编排框架，先用最小实现证明流程。

**验收指标：**固定 15 个任务（5 个无需工具、5 个需要检索、5 个工具失败／不可信输出），逐项记录“是否选对工具、参数是否合法、是否正确停止、完成与否”、工具调用次数和耗时；非法参数 100% 被拒、循环达到步数上限必停、未授权的副作用操作在测试中 100% 不执行。报告任务成功数／15 和不必要工具调用数／5，而不是只演示一段成功对话。若使用模拟模型，明确它只能验证编排与权限，不代表真实模型的决策质量。

## 阶段 6：通用工程能力与工具链选型

**任务：**把工具边界写成 JSON Schema／OpenAPI 或同等结构化契约；练习 HTTP、SQL/全文索引、缓存、任务队列、幂等重试、鉴权与密钥管理，添加最小链路日志与自动化评测。按实际需求选择框架，不把框架数量当作能力。多 Agent 角色协作留到单 Agent 的失败模式和分工收益明确之后。

| 层次 | 常见选择 | 核心问题（不等于全部都要用） |
|---|---|---|
| 流程和状态 | LangGraph、Semantic Kernel | 分支、状态保存、工具调用和人工介入 |
| 数据接入／RAG 流程 | LlamaIndex、Haystack | 加载、切分、索引、检索和评测 |
| Agent 协作（选做） | AutoGen、CrewAI | 多角色分派与协作；不是最小 Agent 必需项 |
| 工具连接协议 | MCP | 向应用暴露工具／资源的接口约定；不自动提供安全授权或任务规划 |
| 向量索引／服务 | FAISS、Chroma、Qdrant、Milvus、pgvector | 从本地索引到持久化、过滤与服务能力，按规模选型 |

**交付：**架构草图、所选组件和不选其他组件的理由、运行说明、评测结果及故障排查清单。

**验收指标：**至少覆盖“正常、超时、工具错误、重复请求、无权限、资料中的指令注入”六类测试；每类有可重现的输入与期望结果，重试不会重复执行有副作用的操作。每条实际调用链能关联请求 ID、检索片段 ID、工具结果、耗时和调用成本（不记录凭据）；比较接入框架前后的任务完成率与 `p95` 延迟，明确复杂度收益和新增故障点。若尚未部署或接入真实服务，将部署／并发指标标为待测。
