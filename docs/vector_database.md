# 向量数据库入门：从相似度检索到 RAG

> 建议先读[文本如何变成 token、ID 和模型内部 embedding](text_to_transformer.md)。本页配套一个[可以离线运行的最小检索脚本](../scripts/vector_search_demo.py)：不下载模型，不需要 GPU，也不需要部署数据库服务。

## 先回答两个问题

**向量数据库是什么？** 它是以向量相似性检索为核心能力的数据系统。通常给每段文档保存一个向量，同时保留它的文档 ID、原文和元数据（如来源、章节）。提问时用**同一套编码方法**把问题转为向量，找出最相近的文档，再取回原文。这是“找候选资料”，**不是**语言模型的 token embedding 查表，也不保证找到的资料一定正确。

**能自己写吗？** 能。少量文档时，保存向量并逐条计算相似度、排序取前 `k` 条，就已经做出了一个有用的**教学版精确向量检索器**；配套脚本正是这个最小实现。但它没有近似索引、并发控制、权限、事务、分布式扩缩容等能力，不应称为可直接上线的完整数据库。数据量大或需持续服务时，可以再研究 FAISS 等索引库，或 pgvector、Qdrant、Milvus 等数据库/服务，根据需求选择。

## 和 LLM 内部的 embedding 有什么不同？

| 对象 | 存储和输入 | 输出与用途 |
|---|---|---|
| Tokenizer | 文本和固定词表 | token ID（整数） |
| LLM 内部 embedding 层 | token ID 索引模型权重矩阵 | **每个 token** 的初始向量，随后进入 Transformer |
| 检索用编码器 | 文档片段或问题的文字 | **整段文本**的检索向量；真实系统通常使用专门训练的 embedding 模型 |
| 向量索引/数据库 | 文档 ID、向量、原文、元数据 | 对问题向量搜索，返回相似片段及其来源 |

这些向量不能因为都叫“embedding”就互换：维度、训练目标和坐标系可能完全不同。向量数据库里的文档向量不是 token ID；RAG 通常把**检索回来的原文**加入提示词，LLM 再自己 tokenize、查模型内部 embedding 表、运行 Transformer。检索编码器可以和生成用 LLM 是不同模型。换检索编码器或版本时应重建文档向量，查询也须用相同版本和预处理方式。

```text
建库：文档 → 分块 → 检索编码器 → 每块一个向量 ─┐
                                                    ├→ 向量索引（ID、向量、原文、元数据）
提问：问题 → 同一检索编码器 → 问题向量 ────────┘
             ↓ 相似度检索 / 可选元数据过滤
       取回候选原文 + 来源 → 组合提示词 → LLM 重新编码 → 生成回答
```

真实 RAG 需要确定分块大小和重叠、如何处理表格/标题、是否做关键词混合检索与重排、如何限制召回文本的 token 数，以及怎样在答案里引用原文来源。检索结果只是外部资料，不应自动把其中的指令当作对系统的命令。

## 最小版：自己动手做一次检索

脚本内置四条演示文档；为保持**完全离线**，把文字转为字符二元组的词频向量，例如“向量数据库”的前几项是“向量”“量数”“数据”“据库”。建库时先从文档构建固定的二元组词表，按词表顺序计数；检索时用**同一词表**编码问题。它只是**词面计数向量**（本例用普通列表存储，很多维度为零），不是经过训练的语义 embedding：“汽车”与“轿车”即使意思接近，也可能因为字符不重合而得零分。

在仓库根目录（包含 `scripts/` 的目录）运行，使用 Python 3.9+，不需要安装额外包：

```bash
python scripts/vector_search_demo.py
python scripts/vector_search_demo.py --query "token ID 如何进入模型？" --top-k 2
python scripts/vector_search_demo.py --query "量子力学"
```

默认问题是“向量数据库怎么检索文档？”。程序会打印编码方法、维度、命中的文档 ID、相似度、元数据与**原文**；默认问题应优先命中 `vector`。查询中没有与建库词表共享的字符二元组时，它报告没有匹配项，而不是编造一个相关结果。示例并非真实语义检索，也不下载 Qwen 权重。

可选地保存/恢复示例索引。仓库默认没有 `results/` 目录；首次使用 `--save` 时脚本会创建目标父目录，生成的 `results/vector_index*.json` 已被 `.gitignore` 排除；文件**只在加 `--save` 时创建**，为避免覆盖已有结果，同一路径第二次保存会报错。`--load` 读取已保存的词表、向量和原文，编码器和格式版本不匹配时拒绝加载：

```bash
python scripts/vector_search_demo.py --save results/vector_index.json
python scripts/vector_search_demo.py --load results/vector_index.json --query "token ID 如何进入模型？"
```

要重复建库可换个新文件名，不要把实验索引提交到仓库。JSON 只用于观察结构，不适合作为并发生产存储；不要从不可信来源加载索引文件。

### 它做了哪些计算？

对于词表里的每一个字符二元组，文档和查询都按同样顺序写成一组数字。设问题向量为 `q`，文档向量为 `d`：

```text
cosine(q, d) = (q · d) / (||q|| × ||d||)
```

这比较的是方向而不是长度；例如 `[1, 0]` 与 `[2, 0]` 的余弦相似度为 `1`，与 `[0, 1]` 为 `0`。余弦对长度不敏感，并不意味着文档越长越相关。空向量没有方向，本例把零向量相似度定义为 `0`，且不返回分数为零的结果。脚本**逐条**对比所有文档、按分数由高到低取前 `k` 条（同分时按 ID 排序）。这叫**精确最近邻检索**；若有 `N` 条 `D` 维向量，计算全部相似度约需 `O(ND)`，本例还会对结果排序（`O(N log N)`）。近似最近邻（ANN）索引可以在检索速度、内存占用和召回率之间权衡，不能简单认为“向量数据库 = 永远精确且全量扫描”。

本例的 `metadata` 只是伴随原文返回，并**没有实现过滤**。实际库常提供按来源、权限或时间过滤的能力；查询时还要确认检索结果是否真正回答问题，不能只看余弦分数高低。不同模型、索引和任务的相似度分数也不宜直接横向比较。

## 如何升级为真正的语义检索？

保留 `ID → 原文、来源、向量` 和检索排序的结构，用**同一个专门的文本 embedding 模型**分别编码每段文档和问题，再指定与该模型推荐方式一致的归一化、相似度度量和输入格式。文档一般先分块并保存来源/位置；编码器输出的向量维度固定，建库和查询的维度必须一致。先用小集合对照手工判断的相关性，观察误召回和漏召回，再决定是否引入 ANN 索引或独立服务。本示例不下载模型，**没有声称用词面二元组模拟了语义理解**。

想进一步接入 RAG，可先把每条召回原文和来源合并成提示词，让生成模型基于这些文字回答，并检查提示词的 token 预算、来源引用和未命中时的行为；生成模型内部仍运行[上一页的 token → ID → embedding → Transformer 流程](text_to_transformer.md)。

## 自测

1. 文档 `id` 与 token ID 是一回事吗？文档的 `vector` 与 LLM 词表中一行权重是一回事吗？
2. 修改 `--query`，找一个字符重合少但意思相近的说法；这个演示会漏掉吗？为什么？
3. 如果保存了旧索引，改用另一个编码模型只编码问题，会发生什么？为什么必须重新编码文档？
4. 为什么检索时要保存原文、来源和 metadata，而不能只保留向量？
5. 文档增多以后，全量扫描和 ANN 索引分别牺牲了什么？
